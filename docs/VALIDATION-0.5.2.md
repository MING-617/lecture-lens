# Lecture Lens 0.5.2 调度与 CPU 能耗验证

测试日期：2026-10-05。Apple M4 / Mac16,1，4 个性能核心、6 个能效核心，24 GB，macOS 26.6.2。电脑接电充电，低电量模式关闭；未改变其他应用或系统电源设置。

## 改动与测量

保留 Nemotron English 0.6B 560ms int8、固定 sherpa-onnx 提交与修订补丁、两个识别线程、两条路径和 0.5 热词权重。只调整模型初始化和音频工作队列的调度；所有音频仍进入识别，不用 VAD 剪掉安静内容。没有新增课程选择或用户设置。

生产队列使用 background QoS，并为音频、结束和取消工作显式 enforceQoS，避免从麦克风或主线程继承更高优先级。初始化使用对应 GCD 队列及 continuation，保留取消后的检查与释放。[Swift SE-0304](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0304-structured-concurrency.md)说明高优先级任务等待低优先级 task handle 可以提高后者的优先级，因此仅降低 detached Task 的优先级不足以作为调度保证。核心分配以实际系统计数验证，不假设所有计算一定运行在能效核心。

在同一候选可执行文件中，明确请求原配置 `2 / userInitiated / cpu`，与 `2 / background / cpu` 串行比较。权重、词表和休眠配置一致。主要语音使用候选／原配置／候选／原配置顺序重复；噪声、静音和停顿各成对比较。采集进程 CPU 时间、唤醒和性能核心时间占比，以及 `TASK_POWER_INFO_V2.task_energy`。

[Apple XNU Recount](https://github.com/apple-oss-distributions/xnu/blob/main/doc/observability/recount.md)与[task.c 实现](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/task.c)表明此能耗字段是系统归因的 CPU 能量，单位 nanojoules；性能核心时间和总时间使用同一 Mach 单位计算占比。计数从模型就绪到处理完成、最终回调排空和工作线程释放，不包含启动加载。CPU 用时可因能效核心速度较低而增多，不能只按 CPU 百分比判断功耗。

这不是整机电池读数，也不包含完整的显示、DRAM 或系统音频功耗。测试期间充电，不能换算成续航提升百分比。启动模型仍需要数秒，这个阶段尚未开始收音；流式字幕延迟另行测量。

## 串行对照

| 输入 | 原配置 CPU 能量 | background CPU 能量 | 减少 | 原／新词错误 | 新最大字幕延迟 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 60.625 秒调参语音，两轮平均 | 41.483 J | 23.210 J | 44.05% | 0／0 | 0.883 秒 |
| 30 秒纯静音 | 23.197 J | 12.285 J | 47.04% | 无字幕／无字幕 | 不适用 |
| 60.625 秒、15dB 噪声 | 45.532 J | 23.516 J | 48.35% | 4／4 | 0.973 秒 |
| 95.625 秒长停顿 | 70.710 J | 36.385 J | 48.54% | 3／3 | 0.867 秒 |

所有最终字幕逐字一致，没有运行错误和超过 3 秒的延迟。噪声各漏 1 词、长停顿各漏 2 词。调参语音的 CPU 时间从平均 16.884 秒增加为 30.030 秒；性能核心时间占比从约 81.89% 降为 29.65%。这些 CPU 时间的增加没有隐藏，背景队列仍能按原速完成。最高排队等待为 0.259 秒。

弃用的尝试也保留：单线程 userInitiated 和 utility 的 CPU 用时较少，CPU 能耗反而更高。单线程 background 发生积压，只有 72 个延迟样本，最大延迟 **31.811 秒**，并有大量遗漏；该结果判定失败，未作为节能收益。Core ML 请求的实测 CPU 能量为 73.190 J，141 词中 2 处错误，对照 CPU 为零错误，因此不采用。没有把 provider 可用或 requestedProvider 标签当作 ANE 加速证明。

## 独立语音与完整词表

独立真人录音按原速运行 349.905 秒：固定的 40 条、10 位说话者、824 个参考词。最终文本与此前已验收的增强版本完全一致，7 次替换、2 次漏词、无额外词，WER 1.092%；首次和最终正确拼写最大延迟均 1.237 秒，超过 3 秒为零，队列等待最大 0.250 秒。

六门课的全部 321 个词条，使用此前固定的 619.633 秒、1,818 词音频按原速连续输入。最终文本与此前已验收的增强版本完全一致：9 次替换、1 次漏词、2 次额外词，合计 12 错，WER 0.660%；首次和最终正确拼写最大延迟均 1.190 秒，超过 3 秒为零。没有运行错误，最大排队等待 0.630 秒、单次处理 0.624 秒。没有把最高排队值截断成较小的短音频结果。

延迟分别统计首次出现、最终正确拼写和全部词片的修订；错误与遗漏另计。原生词结束时间是估计，尚未逐词标注声学真值，也不包含屏幕绘制。完整音频和事件保留在本机，不上传课堂字幕、真人书籍文本或录音。

## 安全性与交付

断言启用的回归检查覆盖停止确认、同步关闭输入、4,001 词完整保存和导出、旧回调隔离、设备中断、20 秒突发输入的积压保护、修订及损坏资源降级。新工作队列始终串行；录音回调的 buffer 先复制，再以独占且不再修改的 buffer 交给工作队列。

实际取消 background 初始化的原生测试通过：模型初始化安全返回后，取消检查阻止安装 worker，未启动音频回调，随后完成释放。新版报告结构也成功读取实际 0.5.0 的 JSON，新增调度与能耗字段为空，旧事件仍可读取。

正式签名的 0.5.2 / build 10 包另以默认参数原速运行 141 词：专业词增强及 CPU 等待休眠生效、两个线程、background 调度、零错误、最大首次及正确拼写延迟 0.990 秒，超过 3 秒为零。该次 CPU 能量为 23.478 J；未将它与不同音频做节能比例对照。

0.5.1 的 ZIP 备份逐文件与原安装包全部 21 个文件相同。0.5.2 已安装至 `/Applications/Lecture Lens.app`，严格签名检查通过，并逐文件确认 21 个文件与已测试的签名包一致。此前 8 份课堂字幕在安装和界面操作后校验值不变。实际打开安装版，悬浮入口和返回主界面均正常，最后停留主界面显示“开始”，没有自动启动麦克风。此次未重新进行实际麦克风声学及整应用能耗对照，也没有替用户改动其他程序。

所有新数值及舍弃的配置保存在 [结构化结果](energy-results-0.5.2.json)，原始事件与文字保留本机缓存。源码、诊断脚本及无原文的验证记录同步到原有私有仓库，以 `v0.5.2` 标记；个人字幕、偏好、录音和模型权重不上传。

本次没有重跑两小时或八小时测试。原 0.5.0 两小时结果保留，不把它当作新版本的测试。这里的验证使用生产转换、识别及结果回调路径的原速文件输入；真实教室、口音、长期电池消耗，以及系统繁忙时的后台调度仍需课堂验证。
